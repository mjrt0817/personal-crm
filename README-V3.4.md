# PersonalCRM Ver.3.4 — 注文書・電子署名・MF請求連携

Ver.3.3＋build-hotfix＋estimate-draft-hotfixを統合した更新版です。

## 役割分担

- PersonalCRM：顧客・案件・見積・注文書・署名状況・受注確定・請求予定。
- 締結ぱっと：注文書PDFをアップロードし、顧客へ署名を依頼。操作・完了確認は手動。
- MFクラウド請求書：受注内容からAPIで請求書を作成。発行者情報・送付・入金・帳簿・申告はMFを正式な管理先とします。
- パーソナルミニ年払いを前提。MF請求先15件、API作成月100件の制限があります。CSV取り込み・合算請求・毎月自動作成は使用しません。

## 更新手順（既存利用者）

1. 現在のコード・Supabaseデータをバックアップします。
2. Supabase SQL Editorで `supabase/migrations/018_orders_and_moneyforward.sql` を1回実行します。既存の001〜017適用済みが前提です。018はトランザクション内で実行します。
3. この更新版のコードで既存リポジトリを更新します。既存の `.env.local` とVercelの環境変数を維持してください。`node_modules` や `.next` は同梱していません。
4. `npm ci` → `npm test` → `npm run build` を実行し、通常の手順でVercelへ反映します。
5. 本番では既存どおり `NEXT_PUBLIC_DEMO_MODE=false` を設定します。trueではサンプル注文書が表示され、保存はできません。

018では本人専用の注文・請求予定テーブル、暗号化したMF認証情報テーブル、非公開 `signed-orders` バケットを作成します。署名済みPDFは画面上4MBまで。新規構築でも既存の導入手順を完了した後、018を実行してください。

## MFの初期設定

1. MFクラウド請求書の発行者情報・振込先・税の計算/端数処理を設定します。インボイス未登録の場合は登録番号を入力しません。
2. MFに顧客と請求先部署を登録します。CRMから自動で取引先を増やさず、請求予定作成時に実在するMFの請求先を選びます。
3. MFの「API連携（開発者向け）」から連携アプリを登録します。
   - 認証方式：CLIENT_SECRET_BASIC
   - コールバックURL：`https://実際のCRMのドメイン/api/mf/callback`
   - スコープ：`mfc/invoice/data.read mfc/invoice/data.write`
4. Vercelに以下を追加し、再デプロイします。
   - `MF_OAUTH_CLIENT_ID`
   - `MF_OAUTH_CLIENT_SECRET`
   - `MF_OAUTH_REDIRECT_URI`（登録したコールバックURLと完全一致）
   - `MF_TOKEN_ENCRYPTION_KEY`（32バイト乱数をBase64化した値）
5. 暗号化キーは `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` で生成できます。秘密値にはNEXT_PUBLIC_を付けず、リポジトリへコミットしないでください。キーを変えた場合はMFへ再接続してください。
6. CRM「設定」→「MFへ接続」で認可します。接続解除はCRM内の認証情報を削除します。MF側の認可も取り消す場合は、MFの連携アプリ管理で別途解除してください。

## 日常の操作

1. 見積書を作成し、有効期限内の「送付済み」にします。
2. 見積詳細の「注文書・電子サインへ」で納期、納品場所、支払条件、検収条件を入力します。
3. 「この見積を確定して注文書を作成」を押します。宛先・発行者・明細・条件を保存し、元の見積と明細はDB側でも変更・削除を防ぎます。
4. 注文書画面の「注文書 / PDF」→「印刷 / PDF保存」。A4、倍率100%、ヘッダー/フッターOFFで保存します。ページ数は明細・条件の長さにより増えます。日本語の長文・多数明細では署名欄のページ位置を確認してください。
5. PDFを締結ぱっとへアップロードし、注文者である顧客の署名欄を配置して送付します。CRMで「署名依頼済みにする」を押します。
6. 締結ぱっとで完了を確認し、署名済みPDF・締結日・任意の管理番号を登録します。PDFのSHA-256を記録し、受注確定と案件への金額反映を同じDBトランザクションで行います。新規案件は「受注」状態で作成します。
7. 受注確定後、注文画面で請求予定を作ります。今回分の数量・単価、請求日、売上計上日、期限、MF請求先を指定します。分割する場合は着手金・残金などを別の予定として作成します。数量0の明細は除外されます。
8. 請求時期に「MFに請求書を作成」。MF作成結果のID・番号・金額をCRMに記録します。顧客へは自動送信しません。MFで確認してから送付します。

## 変更・再送・既存データ

- 注文書作成後に内容変更する場合、署名前は取消→見積をコピー→新規注文書。署名後は原本を残し、変更契約・追加注文として別の見積/注文を作成してください。受注確定後の取消・減額・返金帳票を自動作成する機能はありません。
- 請求予定の合計が受注総額を超える登録はDBで拒否します。未送信の予定は取消後に作り直せます。
- 送信中や通信結果不明の予定は自動再送しません。MFのメモ `PersonalCRM:請求予定UUID` を確認し、作成済みならMF請求書IDを入力して照合します。取引先・メモ・請求日・期限・総額が一致した場合のみ作成済みにできます。
- 送信開始から5分経過後、MFに存在しないことを確認した場合に限り、チェックを付けて予定を未送信へ戻します。作成済みIDが記録されている場合は再送できません。
- MFとCRMで端数処理・源泉徴収等に差が出た場合は「要確認」とします。MFの内容を点検し、必要に応じて調整・照合してください。税率0%の明細は初期実装では `untaxable` として送信します。軽減税率8%にも対応しますが、通常のWeb制作等は10%想定です。税区分や源泉徴収対象の判断はMF側で確認してください。
- 前受金と売上の計上時期は一致しない場合があります。請求書を作成するとMF会計側へ仕訳が連携されるため、前払保守等の売上計上日・前受金処理はMFで確認してください。
- 旧請求書・契約・入金履歴は削除していません。旧データの集計と新しいMF連携分は明示して別表示にしています。旧請求を新連携へ自動移行・合算しません。すでに請求データがある見積から注文書を重複作成する操作は拒否します。
- 注文に紐付いた案件の新規請求は注文管理からMFへ行います。従来の契約請求機能は互換性のため残しているので、同じ契約について従来機能とMF連携の両方で請求しないでください。
- MFの請求書を後から変更しても、CRMに自動で上書き反映しません。入金状況も現時点ではMFで確認します。
- JSONバックアップには注文・請求予定を含め、MFトークンを含めません。署名済みPDF本体はJSONに含まれません。締結ぱっと側の原本も含め別途バックアップしてください。

## 検証

- TypeScript・Next.js本番ビルド。
- PostgreSQL互換PGliteで既存schema＋018を適用し、見積固定、署名前の確定拒否、案件作成、分割請求上限、二重送信防止、状態遷移、ユーザー間分離、非公開ストレージの参照制御を検証。
- API送信データの明細・税率・計上日・照合IDと、不正な入力の拒否を検証。
- サンプルで注文一覧・詳細・設定・請求一覧・注文書をHTTP/ブラウザ確認。スマホ幅390pxで注文詳細の横はみ出しなし。
- MF実アカウントでのOAuth、請求書作成、実際の締結ぱっとへのアップロードは未実施。Supabase本番へのmigrationも未実行です。初回は1件で宛名・明細・金額・仕訳を確認してください。
