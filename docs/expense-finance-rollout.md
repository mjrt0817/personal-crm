# 経費・領収書・管理用PL/BS 導入手順

調査日：2026-11-03。SupabaseへのSQL適用・Vercel上の稼働確認は未実施。GitHubへ反映してもSQLは自動実行しない。

## 既存仕様の確認

- Google OAuth、許可メール、暗号化refresh token、RLSを使用。新機能も既存クライアントとトークン更新処理を使用し、service roleは使用しない。
- 契約・請求・発行済み帳票保護のコードと既存SQLは変更しない。既存 `/api/export/accounting` は請求・入金の元イベント出力のまま。
- 過去チャットで実行された関数権限修正が本番DBに存在するかは、このリポジトリだけでは検証できない。017などの過去SQLを再適用しない。

## 段階1：経費

1. DBバックアップを取得し、既存017適用済みの検証用Supabaseへ `supabase/migrations/018_expenses.sql` を一度適用する。
2. 新規テーブルは `expenses`、`expense_receipts`、`finance_entries`。既存テーブルを変更しない。全て本人のSELECT/INSERTのみ許可、UPDATE/DELETEは不可。
3. `/more` → 経費・領収書。GWS / ChatGPT / ドメイン / サーバー / その他、日付、取引先、事業分税込円額、決済方法、備考を入力する。
4. 現金・事業用預金は `cash`、未払・カードは `payable`、個人立替は `owner`。カード引落は仕訳画面で未払金/現預金を追加する。
5. 取引日範囲・金額範囲・取引先を組み合わせて検索できる。未修正の元経費も履歴として表示される。訂正対象のIDを逆仕訳の備考へ記録する。

外貨、家事按分、消費税区分、海外SaaSの税務判定、適格請求書番号、固定資産、前払費用の期間配分は自動判定しない。外貨額・換算レート・按分根拠などを備考へ残し、会計側で確認する。

## 段階2：Google Drive

1. Google CloudのOAuth同意設定に `https://www.googleapis.com/auth/drive.file` を追加し、設定画面からGoogle Workspaceを再接続する。既存のCalendar / Gmail / Driveメタデータ権限は保持する。
2. 経費を登録後、電子原本または紙スキャンを区別してPDF/JPEG/PNGを添付する（3MB以下）。別々の登録操作であり、アップロード失敗で経費は消えない。
3. マイドライブ直下に `日付_金額_取引先_経費ID_ハッシュ短縮値.拡張子` として新規保存する。フォルダー指定・共有権限の変更・既存ファイルの上書きは行わない。
4. CRMはDriveファイルID、受領形態、元ファイル名、SHA-256、登録日時を保持する。原本バイト列を変換せず送信し、トークンをブラウザーへ返さない。
5. Drive成功後にDB登録が失敗した場合、画面にDrive IDを返す。自動削除しない。タイムアウト・関連付け失敗時は再送前にDriveを照合する。現段階では孤立ファイルの自動復旧・完全な再送冪等性はない。

Drive上での権限変更・削除・改変を防止する機能ではない。ハッシュの記録だけで真実性を保証しない。Drive原本の別途バックアップ、閲覧・ダウンロード可能性、保存期間と運用規程を整備する。CRMのJSONバックアップには証憑本文を含まない。

公式API仕様：[アップロード](https://developers.google.com/workspace/drive/api/guides/manage-uploads)、[権限の範囲](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)。追加権限はアプリが作成・利用許可されたファイルを対象とするdrive.fileで、Drive全体への書込権限は要求しない。

## 段階3：管理用PL/BS・会計連携

- `/finance?year=2026`：PLはその年の経費と手動仕訳、BSは開始時からその年末までの残高を集計。
- 現預金・売掛金・未払金・元入金/事業主勘定・売上・経費に限定した簡易モデル。開始残高を最初に入力し、売上計上・回収を明示的に登録する。売上の借方を売掛金、回収の借方を現預金/貸方を売掛金とすれば回収で売上は増えない。
- 請求書を発行しただけでは売上計上しない。前受・売上認識・契約期間の判断は会計側で行う。貸借一致はデータが全て揃った証明ではない。
- 固定資産・棚卸資産・借入金・前払費用・税金などを含む完全なBSには対応しない。申告用決算書・仕訳帳/総勘定元帳一式の代用にはしない。
- `/api/export/accounting?year=2026`：従来の請求・入金イベントを変更せず維持。
- `/api/export/expenses`：全期間の経費元データ・証憑URL/ハッシュ・手動仕訳参考情報をCSVへ。種類を区別し、安定IDで再出力時の照合を可能にする。freee専用CSV/API連携ではなく、会計担当者が仕訳・税区分を確認して変換する入力資料。請求/入金、経費/手動仕訳をそれぞれ二重取込しない。
- JSONバックアップに3テーブル追加。行数制限による欠落を避けるため500件ずつ読み、100,000件超はエラーにする。CSVは文字列の数式解釈を抑止する。

正式帳簿と申告はfreee等に集約する運用を推奨する設計。自動同期・重複取込防止の取込済み管理・ベンダー固有フォーマット変換は含まない。

## 青色申告と電帳法（個人事業の所得税を想定）

CRMの利用やDriveへの保存だけで青色申告特別控除が受けられるとは判定しない。青色申告承認、所得の種類、正規の簿記、決算書、期限内申告などを確認する必要がある。[国税庁：青色申告制度](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shotoku/2070.htm)

2026年分と、次年度の2027年分を区別する。国税庁は優良な電子帳簿に関する控除が2027年分以降65万円から75万円になると案内し、届出とe-Taxも要件としている。従来の「65万円」の説明だけで2027年分の適用を判断しない。本人の適用区分・届出期限は会計担当者と確認する。[国税庁：電子帳簿保存の取組紹介](https://www.nta.go.jp/about/introduction/torikumi/week/dennsityoubo.htm)

電子取引は電子データの原本保存を基本とし、検索、見読性、改ざん防止、調査時のデータ提出に対応する。検索要件等には条件付きの免除・猶予があるが、この実装では適用を自動判定しない。改ざん防止はシステム以外に事務処理規程の作成・運用という対応もある。紙のスキャンは別制度であり、要件確認前に紙原本を廃棄しない。[国税庁：電子取引データ保存方法](https://www.nta.go.jp/about/organization/osaka/topics/denshi-chobo/pdf/07231206.pdf)

## 本番前の確認

- 検証用DBへ018を適用し、所有者と別ユーザーで閲覧/登録/変更/削除権限を確認する。
- Google再同意後、電子PDF/画像が元のバイト列のまま保存され、日付/取引先/金額と紐付くか確認する。
- Google未接続、権限不足、容量不足、タイムアウト、DB書込失敗を確認する。エラーに秘密情報を出さない。
- 従来の未発行まとめ請求作成・編集、発行済み帳票の編集/削除拒否、契約更新、従来の会計CSVを回帰確認する。
- 期首残高・未払決済・立替・逆仕訳・年またぎと、freee等で確定した数値を照合する。
- 原本バックアップ/復旧、保存年限、規程の実運用を確認後に本番へ反映する。

取り下げる場合はアプリを旧版へ戻し、新規テーブルとDrive原本は保持する。データ登録後にテーブルをDROPしない。
